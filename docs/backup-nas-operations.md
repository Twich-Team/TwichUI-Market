# Native NAS backup operations

Status: implementation/verification candidate; see [progress](backup-nas-progress.md). Production migration and deletion of original recovery copies require the owner's configured destination and explicit action. Existing local storage and live scheduling are preserved on upgrade.

## Browser workflow

Administration → Storage & backups retains Backups, adds Backup Storage, and shows Maintenance health. In Backup Storage choose SMB / NAS, enter a friendly name, private LAN address, username/password, optional domain, regular share and directory. Save, then Test connection. Use Browse NAS folders, breadcrumbs and Create NAS folder to select a directory; save and test that final selection. Passwords stay masked and are never returned after saving; leave the password blank to retain the existing envelope. Active storage credentials/name can be rotated without relocating files. To change the active host/share/path, create a destination and use migration.

The native library does not implement SRVSVC share enumeration. Enter a known share manually; only folder selection inside that share is exposed. No generic remote file manager, arbitrary host paths, shell command, host mount, privileged container, Docker socket or host administrator password is required. Local and existing mounted filesystem choices refer to the installation's approved persistent `/backups` root, including an existing NFS mount. Creating additional host mount points is outside this browser workflow.

Use a dedicated NAS account limited to Market's backup directory. TCP445 by default (or an explicitly configured high port1024–65535), and RFC1918/ULA destinations only; loopback, link-local/metadata, multicast, public IPs and other privileged ports are refused. DNS is bounded and all returned addresses must pass validation; the connection pins one validated address. Native low-level SMB never follows DFS or arbitrary referrals. Signing is mandatory. Required SMB3 encryption defaults on; signed SMB2 compatibility is available by explicitly disabling required encryption on a trusted LAN. SMB1 is absent.

The connection test uses unique `.market-test-…` artifacts, checks read/write/rename/delete and folder creation, and cleans up. Failures are sanitized. Filesystem capacity comes from SMB FileFsFullSizeInformation; unsupported measurements remain unavailable. NAS filesystem capacity includes other NAS files, while Market-managed/protected backup sizes are separate inventory totals. Permission checks prove only what the saved account can do at that moment.

## Migration and outages

A recently successful test is required. Preview reports source, count, bytes, reserve and available space when exposed. Copy, verify and activate queues a durable background job using the existing private manager; scheduled backups wait. A bounded preview token binds the reviewed inventory/revisions and expires after15minutes. Transfers use1MiB chunks and unique incomplete filenames, and are rehashed before finalization. Existing identical archive bytes can be reused on retry; conflicting names fail closed. The original destination stays active on failure/interruption. Creation/protection/restoration metadata is retained, while filesystem identity is updated for the verified destination. Original local files remain intact.

A completed migration offers a SEPARATE “Remove verified original copies” action requiring `REMOVE VERIFIED ORIGINALS`. It rechecks all destination archive hashes first, refuses active recovery references, audits each removal and reports partial outcomes. This action is not executed as part of deployment. An interrupted operation is visible after restart and does not rerun by itself. There is one active, one previous and a small bounded configuration list, rather than a general storage-management platform. Retained original locations remain tracked.

A disconnected destination is not an empty inventory. The last successful inventory remains marked stale, with actions revalidated under the shared backup lock. No write falls back to local storage. Connect/receive timeouts are bounded; tests and browsing have an overall deadline. A later scheduled attempt opens a fresh connection and resumes normally after recovery. Incomplete files are excluded from valid recovery inventory; job failures retain valid backups. Local staging is not used for NAS dumps: pg_dump output streams to SMB, a complete pg_restore decode reads back through a bounded pipe, the SHA256/size is recorded and the archive is finalized only afterward.

## Deletion and restoration

Backups displays creation time, size, destination, protection and verification. Delete one copy with its exact filename, or select up to50 and review their list. Protected deletion requires a separate checkbox; removal of newest/minimum/final restored points requires recovery-loss acknowledgement. The administrator can deliberately proceed. Active `required_by` references cannot be bypassed. There is no intermediate unprotect step. Automatic retention still excludes protected/manual/release/legacy copies and retains minimum recovery points. Deletion audits intent before modifying files and records per-file outcomes; opaque location-specific IDs prevent a retry against a migrated copy from deleting its preserved original. Missing and inaccessible storage are distinguished.

Download streams from the selected storage provider and works with the existing recovery manifest. The service's isolated restore workflow uses a unique `market_test_restore_…` database, never overwrites production, verifies archive integrity first and records restore evidence only on success. It is disabled unless `BACKUP_RESTORE_TEST_ENABLED=true` is deliberately configured with sufficient rehearsal capacity. Real protocol integration tests exercise this workflow against an isolated PostgreSQL17 service. A successful decode or HTTP response alone is not a successful restore.

## Keys, persistence and portability

Configuration, encrypted SMB password envelopes, jobs and audit ledger live in the existing persistent `backup-management-state` volume. Archive manifests live alongside the archives. Encryption reuses `market.provider_secrets` AES-GCM envelopes with a separate backup-specific associated-data identity and the existing owner keyring format. The private keyring file is mounted read-only through `METADATA_KEYRING_FILE`; it never resides in SQLite, API responses, images or Git. Preserve the owner-controlled keyring separately from SQL/manager state, preferably with encrypted off-host recovery material. Losing the keyring makes encrypted credentials unrecoverable. Preserve all older keys while envelopes still reference their IDs; rotate passwords from the browser after a keyring change.

For another Docker host, securely transfer the manager state volume, original keyring, private service token, archive manifests and application database; mount the keyring with ownership/mode accepted by the service. Restore the original environment/secret mounts and use the reproducible manager Dockerfile/lock. NAS configuration contains no Linux host mount path. The existing libpq `PGHOST/PGPORT/PGUSER/PGDATABASE` connection supports independently hosted PostgreSQL; pin compatible PostgreSQL client/server major versions. PostgreSQL infrastructure migration/Komodo/webhooks are not performed here.

## Library selection and limitations

[smbprotocol1.17.0](https://pypi.org/project/smbprotocol/), [upstream implementation](https://github.com/jborean93/smbprotocol), [release history](https://github.com/jborean93/smbprotocol/releases), [MIT license](https://github.com/jborean93/smbprotocol/blob/master/LICENSE). Latest published release inspected November24 was July7 2026; it supports Python3.10+, SMB2.02–3.1.1, NTLM/Kerberos, signing and SMB3 encryption. This installation uses NTLM with a dedicated password and no Kerberos host packages; one maintained Python dependency fits the existing backend and unprivileged container. Upstream has a single listed maintainer; dependency auditing and pinning remain necessary. Share enumeration, DFS, privileged ports other than445 and public NAS addresses are deliberately unsupported. A NAS that hides capacity is reported without estimates.


## Automatic restore verification and the retention gate

The previous recovery receipt expired because it was a one-time operator rehearsal. Scheduling backups did not schedule isolated restorations or renew that read-only receipt. The new optional `backup-restore` service is a separate PostgreSQL17 instance, with512MiB memory,0.25CPU, bounded WAL/logs and no published port. The manager streams the archive into a uniquely named temporary database there, enforces a32GiB database cap and32GiB host-filesystem reserve, captures actual restored table populations/schema, and drops the temporary database afterward. It refuses the production PostgreSQL server as a restore target. The existing production database, collector and credentials are untouched by rehearsal.

With `BACKUP_AUTOMATIC_RESTORE=true`, successful new backups are verified automatically; a failed attempt retries no more often than every30minutes. A successful restore atomically renews the owner-approved local-only recovery receipt and compatibility status. This preserves the existing local-only exception; it does not claim off-VM protection. The expiry is tied to archive creation, not just to a newly written timestamp. A daily backup may cause a brief safe pause while its new archive is being created/restored; it no longer needs routine manual renewal.

The current recovery archive has an operation pin (`automatic-retention`) distinct from explicit administrator protection. Only after a newly restored replacement and durable recovery evidence exist does automation release its own previous pin. Explicit protected flags and pre-existing recovery references are never cleared. Current pinned copies cannot rotate or be deleted. This avoids accumulating a permanently pinned scheduled backup every day. A failed restore/publication retains the previous recovery point. Interrupted isolated databases are named in a durable cleanup receipt; retries remove only that recorded temporary database before allocating another.

Administration shows the last restore, exact expiry when available, latest result, cleanup pause reason and remediation. A missing, stale, inaccessible or corrupt recovery archive keeps destructive retention paused. New raw compaction additionally compares exact variant statistics against source data before the first batch, records a durable content/statistics proof, and rechecks the statistics digest on resumptions. The proof covers all price/supply/count/source fields. Changes to safety/resource code invalidate the existing exact execution document; the owner-authorized operational rollout records the new verified document without shortening any retention period.

### Efficient recovery checks and transfer safeguards

Full archive checksums, complete decode and actual isolated restoration run when creating/verifying a new recovery point. Between those full checks, cleanup uses a private manager record and a bounded file-identity/protection check under the shared lock; it does not re-read gigabytes over SMB every minute. A changed identity, inaccessible storage or expired archive pauses cleanup. The identity includes SMB write/change timestamps. NAS downloads stream promptly with an `X-Checksum-SHA256` header and the existing manifest for independent verification; restore/migration/deletion still validate the complete checksum. Local downloads retain their existing pre-stream hash check. The only compatibility adoption is a fresh, owner/service-owned local restore receipt, after a new complete checksum; NAS manifests alone cannot establish trusted recovery proof.

Incomplete transfer names are journaled before writing. A restart marks the job interrupted and records only its known incomplete file for bounded cleanup. New transfers retry that cleanup first; administration also provides “Retry incomplete backup cleanup.” Unknown partial files are preserved rather than treated as authorized deletion candidates. Deletion reconciliation skips remote I/O at startup so an unavailable NAS cannot prevent configuration recovery. Only bounded, previously authorized orphan-manifest cleanup runs later.

Migration checks for aliases using a harmless unique marker before copying or deleting originals. Two names for the same local/mounted/SMB folder are rejected. Protected original-copy cleanup requires its own explicit acknowledgement. The legacy local operator helper refuses NAS cutovers, unavailable manager state and a checkout that does not own the active archive root; it cannot silently create a local fallback. Use the native administration workflow after NAS activation.

Regular hidden NAS shares such as `Backups$` are supported through manual share entry. Administrative drive shares, `ADMIN$` and `IPC$` are refused. An explicitly configured high port is supported, while connection attempts remain role-restricted, private-LAN-only, SMB-specific and rate-limited.

### Completed reservations versus active use

Historical release manifests can retain completed `required_by` reservations. These remain excluded from automatic rotation. The delete dialog identifies them and requires explicit acknowledgement together with protected-copy and recovery-loss confirmation; deletion does not first clear protection or reservations. Actual restore/migration use and an unexpired120-second cleanup recovery lease cannot be overridden. Pausing cleanup and waiting for its lease to expire permits a deliberate current-copy deletion, which then pauses cleanup until another verified copy is available. This preserves both administrator control and the recovery prerequisite during actual deletion batches.

Removing verified original copies runs as a background operation with final per-copy results. Protected originals and inactive reservations require explicit acknowledgement. Current active references remain retained. No production original-copy cleanup is part of the release.

## Approved production release and rollback

The owner approved the nine-scene UI gallery and explicitly authorized merging PR54 and deployment after final checks. `compose.backup-nas-release.yaml` is a focused production definition reconstructed from actual running container configuration, with private original environment files under ignored `.local/backup-nas/production`. It preserves published ingress, existing external networks/volumes, resource limits and original secret mounts. Set the four `MARKET_NAS_*_IMAGE` variables to verified immutable image IDs. Validate with `config --quiet`; never print resolved configuration or environment files. Start only `backup-restore`, then explicitly scope replacement to `backup-manager api local-api retention worker monitor proxy`; never use an unscoped `up` or remove orphans. The collector image changes only bounded housekeeping code; its loop/environment/schedule remain unchanged.

`compose.backup-nas-rollback.yaml` pins the seven original immutable images and exact original settings/mounts. With the private environment files preserved, a scoped `up -d --no-deps` of the affected services restores the original runtime. Pause automatic retention before rollback; restore compatibility is additive and no schema migration is required. Preserve the new restore service/data until its jobs have stopped; retirement of its derived temporary database volume is separate from archive retention. Keep this release worktree and private files until superseded by a verified later procedure. These host paths describe this installation's release, not the portable NAS configuration.

### Companion daily pricing dependency

Canonical daily pricing is a separate opt-in cache from the legacy compact statistics. Before raw deletion, daily closing snapshots in a market already using canonical pricing require a sealed, complete canonical derivation. Automation prepares missing support in at most500complete variant groups per cycle, using the existing derivation code and advisory lock. Complete groups commit independently and safely resume; the derivation becomes usable only when every original listing is accounted for. Existing on-demand preparation resumes the same cache. Preparation holds no collector lock, has bounded statement/transaction limits, preserves the existing300,000-listing source bound and does not activate a pricing default or change bridge contracts. Missing/corrupt support preserves raw data and appears in maintenance health.

### Optional derived pricing cache retention

The audit found `bridge_derived_records` had no cleanup path: deleting legacy intraday statistics did not remove the separate derived cache. The optional `RETENTION_CANONICAL_CACHE_PRUNING=true` stage uses the same90-day intraday eligibility, preserves every current market head and all retained daily closing references (including60-day support), invalidates only the affected stale derivation markers, and removes at most the authorized row batch per transaction. Repeated execution safely resumes. It is disabled by default because it introduces a previously unpruned data category. The production dry run reports zero eligible rows today. Production enablement requires the owner's separate explicit approval and a new exact execution document; it is not implied by deployment or by the earlier raw-listing cleanup approval. Health displays whether it is enabled. The release definition defaults its `MARKET_RETENTION_CANONICAL_CACHE_PRUNING` setting tofalse.

Keep a previous destination reachable while it still contains tracked recovery copies. An inaccessible previous inventory is reported unavailable rather than empty. After explicit original-copy cleanup confirms that no backup archives remain, Market retires that previous location; disconnecting the retired NAS cannot block the new active destination. Unknown archives and partial cleanup keep the previous location tracked.

Scheduled backup failures now record a terminal failed job and retry after30minutes (or the shorter configured cadence). A storage-preflight failure or brief competing operation cannot leave a queued reservation blocking every later scheduled backup. Successful scheduling retains the original cadence. Network failure during temporary-file cleanup remains a recorded incomplete cleanup, rather than undoing the failed-job receipt. No failed attempt rotates recovery copies or falls back locally.

A migration retry subtracts existing same-size filenames when estimating remaining transfer space. That estimate never establishes integrity: the background job rehashes every existing candidate and refuses a checksum conflict before reuse. The dialog distinguishes existing copies from bytes still needing transfer. Source backups remain intact on all failures.

Retention cycles reserve enough time for their final bounded transaction rather than starting it at the overall deadline. Aggregate integrity exceptions explicitly pause/disable future cleanup and retain the affected source; administration shows the cause. Successful budget exhaustion is distinct from an integrity failure. An operator must review and repair integrity before resuming; code/scope changes still invalidate the exact execution document.
