## Architecture and research decisions

Retain Tauri 2, the lightweight vanilla desktop interface, Rust HTTP/protocol/cache core, existing SQLite schema/generations and Windows Credential Manager. Do not introduce a second desktop research application or a heavy frontend framework. Tauri owns tray/window lifecycle; a Rust worker owns scheduling and all sync operations regardless of WebView visibility. The scheduler has an injected wall clock, one active run identity/cancellation generation and bounded retries. Clock jumps/wake cause one reconciliation, never a burst of catch-up jobs. Persist nonsecret settings atomically with a version and safe legacy connection migration. Never persist pause/hidden visibility as accidental first-run onboarding suppression.

Use the supported Tauri [tray](https://v2.tauri.app/learn/system-tray/), [single-instance](https://v2.tauri.app/plugin/single-instance/), [autostart](https://v2.tauri.app/plugin/autostart/), [window-state](https://v2.tauri.app/plugin/window-state/) and [opener](https://v2.tauri.app/plugin/opener/) integrations. Register single-instance first. Rust validates settings and invokes OS integrations; the WebView receives only narrow app commands/events, no unrestricted shell/file/network permissions. Autostart is opt-in/reversible. Window geometry can restore without restoring hidden/closed state on first run. Actual Windows installed tests, including native tray and process behavior, are required; Linux mocks never establish native acceptance.

Browser authorization follows [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html), [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html) and [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html): public native client, PKCE S256, cryptographic transaction state, an exclusively bound 127.0.0.1 ephemeral-port listener and exact registered callback path. The server returns only a short-lived single-use authorization code to that callback after authenticated account/device consent. Tokens never enter browser URLs; access/refresh credentials stay in Credential Manager. Rotate refresh credentials with family/replay revocation, expiry, bounded attempts and a documented crash/retry strategy. Browser-session approval requires normal CSRF/origin protection; native token exchange requires the transaction's verifier/redirect/state bindings. Reject redirects with other hosts, userinfo, fragments, arbitrary paths or ports not matching the initiated transaction. Passwords remain in the normal invitation-only website login. Preserve old device tokens and REST v1 sync/export contracts.

Add a separate device grant/activity model and additive migrations; old credential fields retain their meaning. New companion credentials have narrowly bounded native permissions and a distinct kind that older API binaries reject after rollback, preserving their scope boundary; legacy device tokens remain unchanged. A companion bootstrap response exposes the account, available verified markets, safe preferred-market choice and source/check freshness without making the existing browser-only full preference API generally writable by devices. Device status is server-confirmed; a local claim that installation completed never marks pairing/first sync complete. Ownership applies to every approval/status/rename/revoke/renewal operation. Revocation also revokes refresh family access, while local offline data remains until explicitly cleared.

Permanent, versioned installer assets are published from verified Windows builds through an explicit release gate. A normal account can download without GitHub authentication or temporary workflow-artifact URLs. [Tauri updater signatures](https://v2.tauri.app/plugin/updater/) are required independently of Windows Authenticode; neither private key is committed. Implement safe update checking and signing/release infrastructure, with no silent unsigned payload installation. Missing owner signing credentials/certificate expenditure is an explicit external decision, not permission to call an unsigned candidate stable/production-ready. Keep new major website/desktop designs in review candidates until explicit owner approval; the earlier website approval does not approve these new surfaces.

## Checkpoint discipline and external gates

At each coherent verified checkpoint inspect the diff, secret/unrelated-file exclusions and relevant test evidence; commit/push on the development branch and record exact hashes/results. Test only isolated market_test databases destructively. Use bounded rootless containers; no host package installation. Refresh implementation/progress at each cycle and keep unresolved work explicit. The [progress ledger](companion-v2-progress.md) is the continuation entry point; full completion is the original request's end state, not the first successful subtask.

External gates: owner review of the significant new desktop/web designs after the eight actual screenshots; owner-managed Authenticode/updater signing keys and any certificate cost; any genuinely unavailable external release capability. Do all independent engineering and produce a concrete reviewable release before asking for final promotion approval. Never treat elapsed time as approval or erase a gate by renaming a release.
