## Production keyring prerequisite

The [operations runbook](item-metadata-recovery-operations.md) remains authoritative for backup/rotation/rollback. An operator must provision a separately backed-up private keyring, outside Git, SQL volumes/dumps and CI/artifact directories: JSON `{"active":"key-2026","keys":{"key-2026":"<base64 of 32 random bytes>"}}`. Generate the random value in the owner's approved secret system. This is the AES-256-GCM encryption key, distinct from the Everloot API key and Companion updater signing key; never reuse either.

Both API and enrichment must see the same regular, non-symlink file, owned by their effective UID (image UID 10001 with the actual rootless host mapping), mode 0600/0400, via `METADATA_KEYRING_FILE`. Verify only successful loading/readiness in both processes; never print file contents or credentials. Restore SQL plus the separately restored matching keyring in an isolated rehearsal. Retain historical key IDs for retained backups.

The optional overlay currently bind-mounts a **single file inode**. Renaming a replacement host file does not update that mount. Prefer an owner-reviewed private **directory** mount with atomic replacement inside it, preserving owner/mode, or a controlled metadata/API remount when rotating the master key. An in-place write is not atomic; do not rely on it for uninterrupted rotation. API-key replacement in the browser is separate and needs no master-key change or container restart. Master-key rotation uses the existing transactional rotate endpoint after both processes can read the new keyring; keep old IDs for old backups.

On the isolated DB, each before/after export uses a short `REPEATABLE READ, READ ONLY` transaction with a 5-second statement timeout. The operator uses its existing private DB connection (no password/DSN in evidence). For example, bind psql `snapshot_id` and quoted `region` from the manifest, then export these **SELECT results** as canonical CSV through the operator's client:

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;
SET LOCAL statement_timeout = '5s';
SELECT DISTINCT item_id FROM snapshot_statistics
WHERE snapshot_id = :snapshot_id ORDER BY item_id;

WITH ids AS (
  SELECT DISTINCT item_id FROM snapshot_statistics WHERE snapshot_id = :snapshot_id
)
SELECT i.item_id, m.name IS NOT NULL AS primary_named,
       m.fallback_name IS NOT NULL AS supplemental_named,
       encode(sha256(convert_to(coalesce(m.name,m.fallback_name,''),'UTF8')),'hex') AS name_hash,
       m.http_status, m.synthetic, m.catalog_json, m.details IS NOT NULL AS primary_attributes,
       m.fallback, a.asset_hash IS NOT NULL AS local_icon
FROM ids i LEFT JOIN item_metadata m ON m.item_id=i.item_id AND m.region=:'region'
LEFT JOIN item_media a ON a.item_id=i.item_id AND a.region=:'region'
ORDER BY i.item_id;

-- Export and hash the ordered original price/supply rows separately.
SELECT item_id,variant_key,algorithm,recent_price,lowest_buyout,supply,priced_supply,listing_count
FROM snapshot_statistics WHERE snapshot_id=:snapshot_id ORDER BY item_id,variant_key;
COMMIT;
```

Also export the selected IDs' `metadata_sources` normalized fields/provenance/status/retry timestamps per provider/locale, omitting credential/provider-secret tables entirely. Inspect existing legacy names for placeholders/synthetic provenance before counting; SQL non-null flags are candidate availability, not independent semantic verification. Separate local icon bytes from external icon references and class/slot/level/binding/vendor/lines availability from mere catalog-row existence.
