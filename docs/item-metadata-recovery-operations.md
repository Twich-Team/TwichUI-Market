## Secret setup, backup and restore

The sole new runtime setting is `METADATA_KEYRING_FILE`, a private JSON keyring mounted read-only into API and enrichment processes. The optional `compose.metadata.yaml` overlay uses `METADATA_KEYRING_PATH` on the owner-managed host; that file must be outside the repository, PostgreSQL volume, database backup directory and browser artifact directory. Its owner must match the effective API/worker UID (image UID 10001 under the rootless mapping) and mode must be 0600 or 0400. Symbolic links, group/world permissions, invalid AES key lengths and unknown key IDs fail closed. No fallback plaintext/database encryption key exists.

Generate a 32-byte random AES key using an approved secret manager, encode it with standard base64, and provide JSON of this shape through that manager: `{"active":"key-2026","keys":{"key-2026":"<base64 of 32 random bytes>"}}`. Do not paste actual keys into chat, shell history or this document. Mount the same keyring into both processes. Existing Blizzard OAuth stays in its established private environment controls and is not copied into PostgreSQL.

Back up the keyring in the owner's separate encrypted secret backup system, independently of SQL dumps. SQL contains AES-GCM ciphertext/nonce, key IDs and configuration, with provider ID bound as associated data. Restoring SQL without the matching keyring cannot recover credentials. A restore rehearsal must use isolated PostgreSQL and the same externally restored keys; verify decryptability through a bounded worker connection test, never by displaying secrets. Store previous keyring versions until all required backup restore points have migrated or expired.

Once the mounted secret is installed, administrators can add/replace provider API keys from Administration → Data Sources without restarting Docker. The API only stages an encrypted candidate; the dedicated worker validates the actual documented response under the existing budget/cooldown. A success atomically replaces the active envelope. 401/403 or unsupported keys leave the old envelope and expiry unchanged. Network/rate-limit failures leave the candidate pending and back off. A provider-side key revocation cannot be reversed by this app; if the provider invalidates an old key at rotation, replace it promptly. Store the provider's actual expiration date to receive 30/14/7-day warnings. No full-key read endpoint exists.

## Encryption-key rotation

1. Add a newly generated random key under a new ID to the separately backed-up keyring, retain old IDs, then select the new ID as `active`. Keyring reads are dynamic. Prefer an owner-approved private directory mount and atomically replace the file inside that directory, preserving owner/mode; verify loading inside both processes without printing contents. The optional overlay currently binds one file inode: renaming the host file will not update that mount, and an in-place write is not atomic. With that overlay, use an approved controlled API/enrichment remount for master-key replacement, or change to the reviewed directory mount before rotation. Routine provider API-key replacement through Data Sources does not change the master key or require a restart.
2. As an administrator with a current CSRF-protected browser session, POST `/api/v1/admin/metadata-providers/rotate-encryption`. It re-encrypts active and pending envelopes in one transaction using the current active key; it emits only a count/audit event. Unknown old keys or authentication failures roll back the entire operation.
3. Verify every non-null envelope key ID uses the new ID and bounded connection tests succeed. Keep old key IDs in the separate recovery keyring for older SQL backups. Never remove a key merely because the current database no longer uses it.
