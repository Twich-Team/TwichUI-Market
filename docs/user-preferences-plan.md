# Persistent personal preferences

Owner objective: server-side, per-user website preferences across sessions/devices, with automatic saving and a small Account & devices reset section. Keep the new frontend in preview pending explicit promotion approval. Preserve collector, market history, administration and desktop REST contracts.

1. Add migration 0012 and a strict versioned self-service preferences API. Browser ownership/CSRF, bounded payloads, safe defaults, current-market resolution, optimistic revisions and atomic reset. Verify PostgreSQL isolation, concurrent first writes/updates, invalid fields, unavailable-market fallback and migration parity/rollback safeguards.
2. Add account-scoped TanStack Query loading and a serialized optimistic save queue. Merge dirty fields over fresh server state on revision conflicts; retain/retry pending choices on connectivity loss; ignore stale responses after subsequent choices, reset or account changes. No browser persistent storage of private preferences.
3. Restore preferred market, Explorer range, catalogue size/columns/sort and Deal Finder mode/filters. Add compact My Preferences/reset/status controls. Saving preferences cannot change collection schedules. Graceful fallback must retain an unavailable saved market. Preserve existing selection, pagination, variants and exact-price behavior.
4. Verify frontend queue/cache logic and real Chromium persistence across independent sessions, multiple users, rapid changes, conflicts/offline recovery, reset and fallback. Run existing PostgreSQL/frontend/browser/Windows CI and push verified checkpoints.
5. After a valid backup, apply only the additive schema and deploy the candidate to the existing bounded localhost:18444 preview. Permit only authenticated personal preference mutations in its otherwise read-only API. Retain production frontend/collector images and history, verify live preview/TLS/resources, inspect screenshots and deliver the review URL/evidence.

Schema 1 uses a fixed allowlist and defaults, a per-user revision and partial updates. Compatible additions receive defaults; incompatible changes require a version/migration. Reset increments revision so pre-reset writes cannot revive an old document. Historical disabled markets are available research choices; absent markets fall back to the enabled feed, then the first available market, without rewriting the stored choice.
