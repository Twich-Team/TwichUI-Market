## Collector

The collector is opt-in: `docker --context rootless compose -f compose.yaml -f compose.tls.yaml --profile collector up -d worker`. It does not run for disabled or unverified markets. Do not mark markets verified until S1 live evidence establishes their mapping and payload semantics. Set BLIZZARD_CLIENT_ID/BLIZZARD_CLIENT_SECRET in ignored .env; they are passed only to the worker. OAuth tokens remain in worker memory. Never print Compose's rendered configuration because it contains credentials.

Collection is sequential across processes using a PostgreSQL advisory lock. Failed payload ingestion rolls back while the failure run is retained. HTTP errors trigger bounded exponential backoff, honoring Retry-After up to 24 hours. Polling is at least five minutes. Source modification timestamps stay separate from successful HTTP check time. A 304 reuses existing contents without inventing an upstream modification. Missing auctions arrays fail closed until empty-house behavior is verified. The default MAX_DATABASE_BYTES is 5 GiB; reaching it suspends new ingestion rather than deleting long-term history. This is a collection guard, not a filesystem quota: leave disk headroom for WAL, backups and other VM uses. No raw response bodies are retained.

Item-name resolution runs at most once per 15 seconds and only for enabled/live-verified markets with observed items. It queries the region's static-forever namespace, validates returned identity/name and stores successful lookup provenance. Successful names refresh after 30 days; missing names retry after seven days, other failures after at least 15 minutes. No cross-game namespace fallback is invented. Rate-limit cooldowns are shared across collection, OAuth and metadata requests. Authorized HTTP requests never follow redirects. Administration exposes unresolved-name status and retry times. Live static-forever-us lookups and genuine missing-item 404 responses were observed on 2026-11-14; see the evidence files.

## Backups and restore rehearsals

Start daily backups with `docker --context rootless compose --profile operations up -d --build backup`. The bounded PostgreSQL-client container uses no Docker socket or host scheduler. It takes a custom-format dump at startup and every BACKUP_INTERVAL_SECONDS (default 86400, minimum 3600). BACKUP_KEEP defaults to seven archives (1–30). MAX_BACKUP_BYTES defaults to 2 GiB total; a further 2 GiB of free filesystem headroom is reserved before starting. Insufficient budget stops backup creation for operator review. Rotation happens only after a successful dump and never deletes market history.

Archives and manifests are in ignored backups/ (directory 700, files 600). They contain private application data; arrange an owner-managed encrypted off-host copy for disaster recovery. This implementation verifies local restoration but does not provide off-host durability. API administration reads only a separate status mount, not archives or credentials. Backups use PostgreSQL's consistent pg_dump snapshot, atomically rename completed archives and record SHA-256. Shared locking serializes the scheduled worker, manual backup and restore verification.

Manual dump: `python3 scripts/backups.py create`. Restore rehearsal: `python3 scripts/backups.py verify-restore backups/<archive>.dump`. The rehearsal verifies SHA-256 and size, starts a fresh memory-limited PostgreSQL instance without a host port, runs pg_restore with constraints, queries revision/data counts and records evidence before removing that disposable instance. It never restores over the running application database. The 512 MiB tmpfs rehearsal supports current small datasets; larger backups require a separately planned bounded restore volume and sufficient capacity.

Run `python3 scripts/verify-backup.py` for a repeatable nonempty synthetic-data rehearsal plus corrupted-archive rejection. It uses dedicated twichui-market-recovery and twichui-market-restore projects, separate from regression tests. Verified locally on 2026-11-13: synthetic administrator, market, observation, listing and buyout sum survive restoration; corrupted archive rejected. A real scheduled development archive (currently empty application data) was also restored successfully. Persistent development PostgreSQL retained migration 2541add7d379 across restart, and the HTTP health check recovered with 200.

## Operational retention

`python -m market.maintenance` reports a dry run; `--apply` prunes operational records. The collector invokes this once per day. COLLECTION_LOG_DAYS defaults to 90 (range 7–3650); SECURITY_EVENT_DAYS defaults to 365 (30–3650). Login rate-limit windows older than one day and expired credentials/invitations older than 30 days are pruned. No automatic database vacuum-full or host disk maintenance is performed.

Historical compaction is implemented but defaults OFF (`HISTORY_COMPACTION_ENABLED=false`) while exact Workshop reference formulas remain unverified. Raw records may be needed to validate a compatible algorithm; no production raw data is pruned under the default policy. After the desired formulas and retention have been verified, `--compact-history` or the corresponding environment setting enables bounded detail retention. Defaults are RAW_LISTING_DAYS=2 and DETAILED_STATISTICS_DAYS=64. The latest snapshot of every market is protected, as are all daily end-of-day reference samples indefinitely. Every fetch observation, payload/content hash, source namespace and upstream timestamp remains preserved. Statistics carry their algorithm version.

Tests verify that 500-day-old daily prices/provenance remain queryable after raw cleanup, 14/60-day values do not change, and deduplicated snapshots can rehydrate their details if contents recur. Non-daily detailed samples outside retention may be compacted; sync returns 409 when a cursor requires unavailable detail, and the companion automatically starts a complete refresh while preserving its completed offline cache. Downgrading the statistics migration after raw compaction is explicitly rejected; restoration from a pre-compaction backup is required for that rollback.

Synthetic capacity check: 100,000 listings, 9,788,909-byte JSON payload, 6.099 seconds and 257,096 KiB peak RSS in a 384 MiB/one-CPU test container. This is synthetic performance evidence, not an upstream payload observation; production worker CPU remains limited to 0.5 CPU. Reproduce with scripts/benchmark-ingest.py in a dedicated disposable market_test database.

The default `monitor` container independently records PostgreSQL database allocation once per UTC hour, even when live collection is disabled. It uses a transaction advisory lock, retains 90 days (at most 2,161 hourly samples), and has 128 MiB / 0.25 CPU limits. Administration displays actual recorded size changes, signed average daily change and recent measurements. No growth rate is reported until two distinct hourly samples exist. This measures PostgreSQL allocation, including maintenance; it is not a forecast or a measure of completed sales. The sampler retries safely after failures and does not log connection details. The collector's 5 GiB guard remains separate.
