# Workshop connection repair

This repair starts at beta.7 integration `d56d3ca` and preserves the published installer. No signing, publication, deployment or player-data operation is authorized here.

## Findings and trust boundary

The owner supplied the visible failure, not native diagnostics or a genuine Forever executable. Its exact trigger remains unknown. Confirmed source defects are (1) `installation::validate_game` and `validate` call `delivery::owned` on the game root, Wow.exe and installed addon inputs, applying a private output/staging owner policy to read-only files; (2) the UI erases almost every actual error with a generic message; (3) native setup failures are absent from saved diagnostics. Windows fixtures reset their parent ACL to the runner identity and use an explicitly synthetic 1.60.1 version resource. Their success cannot establish owner-PC compatibility.

Flow: authenticated account/verified market → remembered configuration → bounded discovery → native picker if ambiguous → game root → native PE version → addon contract → existing output/receipt preflight → current account/origin/market recheck → expiring native confirmation. Only confirmation persists permission; the existing native worker handles later downloads. Before confirmation, no summary API call or game-file write occurs. Discovery suppresses invalid candidates, so a picker selection is the authoritative source for actionable validation errors.

Generic beta.7 failures can originate from an unavailable account/market, saved configuration read/parse, picker COM/path conversion, ownership/ACL checks, missing root/Interface/Wow.exe, native version resource mismatch/unreadability, missing/invalid/unreadable addon contract or Lua files, unknown/unsafe Market directories, invalid legacy artifact/receipt or another account/market, changed setup context, expired review, randomness, or internal synchronization locks. The owner's pre-confirmation report rules out the later summary download/publication as its immediate cause.

Installed game/addon inputs now require bounded reads, exact contract/version checks, local fixed-disk paths, and component-level reparse/alias refusal; their owner need not be the player. The Companion never executes or modifies these inputs. The AddOns output parent permits the current user, their token owner, Administrators or SYSTEM as owner, still rejects unrelated write grants, and uses a read-only `CreateFileW` access request to verify effective create rights. Existing Companion-managed folders/files retain the strict original user/token-owner policy, receipts, allowlisted filenames, integrity checks and atomic publication. Inherit-only ACEs do not grant access to the object being checked; effective grants on created children remain checked. No ACL is changed by the product. Broad shared-write installations remain refused as unsafe destinations.

The 1.60.1 version prefix has **not** been broadened: there is no genuine Forever PE resource evidence. Unsupported-resource diagnostics include the observed numeric version. A real binary with different metadata may still be refused; evidence from the owner's failed validation is required to correct that identification policy safely.
