## Provider-results investigation

Read-only production queries confirmed persistence and reproduced the scope mismatch without creating a session, requesting metadata or queuing recovery. At the recorded candidate-handler sample, **1,807 tasks** existed: **3** for the first market and **1,804** for collecting market 2. The owner's stored preferred market was 2, but administration's own selector initializes to the first market. The three market-1 tasks were created shortly before this work; before those tasks existed, that filter would have returned no rows (inferred from their persisted creation times).

Actual stored outcomes include 59 recovered names, 75 historical metadata responses with unrecorded gains, missing results, one attributes-only result, returned-but-unimported names, observations and skips. These totals change through the already-running worker; they are point-in-time evidence, not fixed application counters. No access-blocked attempt exists in this sampled task history. Earlier operator/probe failures were not necessarily persisted as recovery tasks; current source rows and legacy backfill are not an immutable attempt ledger. Those absent records and field-level deltas cannot be reconstructed honestly. New normal recovery results already persist HTTP status, returned fields, committed field gains and outcome; no persistence migration or recovery campaign is needed for the demonstrated visibility defect. The table represents the latest result per recovery task with its attempt count, rather than claiming a separate retained record for every historical retry.

`MetadataTask.result_json`, source state, job association, date handling, query ordering and pagination were inspected. The existing endpoint succeeds on real persisted records; no authentication, UTC conversion, default-date, query exception or data-loss defect reproduced. The default sort is latest task update then descending ID. Existing task/job indexes and bounded live timings do not justify an unrelated index migration. Isolated API/browser tests cover administrator/member boundaries, redaction, empty/default/filtered states, local filters, pagination, ordering, historical qualification and HTTP 200 without recovered fields.

The reproducible read-only diagnostic is `scripts/diagnose-provider-results.py`; PostgreSQL enforces `transaction_read_only=on` and a ten-second statement timeout. It emits the existing safe response allowlist and aggregate counts. It neither authenticates a real production HTTP session nor claims to do so; HTTP authentication is tested in the isolated suites.

## Performance and layout stability

With an imposed **1,600 ms** page response, the released table collapsed from **620 px to 52.92 px** (−567.08 px), moving its footer in document coordinates by −475.39 px. The candidate stays **620 px**, with **0 px table-height change and 0 px footer movement** during replacement; internal scroll stays at 100 px. A newer 180 ms page response beats the earlier slow request. Errors retain the last successful rows and show a visible alert/retry.

These are user-triggered geometry measurements on controlled fixtures, not a Core Web Vitals CLS score or production p95. Fixture capture time and data freshness differ between before/after sessions. At 1440×1000, the first item row moved from **722.64 px to 501.64 px** (221 px higher), and search from 298.39 px to 250.70 px. Fixture warnings remain in both interfaces; normal verified production markets need fewer warnings.

Three isolated contexts measured medians of **1,069 ms** through fixture sign-in to populated catalogue, **1,013 ms** to exact research, and **83 ms** for Back. Returning made zero catalogue requests. Initial encoded JavaScript is **164,293 bytes**, compared with the earlier released-review receipt's 148,782 bytes (about 10.4% higher); the shared accessible menu accounts for additional initial UI code. Explorer still requests no ECharts bundle. These are bounded local samples, not general production latency guarantees. [Layout measurements](evidence/everyday-polish/layout-measurements.json), [pagination](evidence/everyday-polish/pagination-measurements.json), [navigation/bundle](evidence/everyday-polish/browser-performance.json), [read-only handler timings](evidence/everyday-polish/production-handler-performance.json).

Released catalogue timings were 611.17 / 401.71 / 394.03 ms and candidate 322.10 / 82.23 / 84.63 ms; exact Details timings were released 177.68 / 92.41 / 17.68 ms versus candidate 67.28 / 20.13 / 18.78 ms.
