# Native authorization contract and security checkpoint

Current status: the Rust authorization/renewal runtime and website consent/device surfaces are now implemented and pass actual installed Windows browser approval, restart, revocation and legacy upgrade checks (465ee0d/run43651343091). The implementation-pending statements below describe the earlier backend foundation checkpoint. Production remains on schema0012; no v2 migration/promotion is implied. See [current progress](companion-v2-progress.md) and [release gates](companion-v2-release-operations.md).

Implementation candidate only; production remains on schema 0012 and the approved frontend/API. This contract is additive and does not replace legacy device tokens, browser sessions or the existing sync/export wire format. Native integration and browser approval UI are subsequent milestones.

The public Windows client identifies as `twichui-market-companion`. POST `/api/v1/companion/authorizations` accepts a readable device name, platform Windows, app version, cryptographically random state, S256 challenge and exact ephemeral `http://127.0.0.1:PORT/companion/callback` URI. The server returns a five-minute browser approval URL under the configured issuer. No password, refresh token or access token belongs in a URL. Consent requires an authenticated browser session, existing CSRF/origin protection and a consent proof bound to that session, account, transaction and expiry. Approve and deny each consume the pending decision. The approved account/session must still be valid when the client exchanges its code.

POST `/api/v1/companion/token` uses bounded form encoding. Code exchange requires the exact redirect, state and PKCE verifier. Codes expire after 60 seconds, are stored hashed, and can be consumed once under a PostgreSQL row lock. Five incorrect proofs invalidate the transaction. Authorization creation and token exchange have shared database rate limits, bounded transaction population and bounded expiry cleanup restricted to these new protocol rows. Missing server signing configuration fails closed.

Successful exchange creates a distinct `companion` credential kind, one-hour access token and owned device authorization capped at 90 days. Refresh expiry is 30 days of inactivity, capped at the authorization expiry. Every renewal rotates both secrets and revokes prior access credentials. Native scopes permit only account identity, market/bootstrap/observation reads, sync, device activity and self-revocation. Administrator status never expands these scopes. Full website preferences, other devices, administration and collection/retention changes remain unavailable. Legacy `device` credentials keep their old behavior.

Before requesting renewal, the native client must atomically save a fresh random `rotation_nonce` alongside the old refresh token in Credential Manager. It retries an interrupted renewal with that same pending nonce. The server returns the same derived credentials for an exact retry within five minutes; a different nonce, older refresh generation or expired retry revokes the whole native family. All consumed refresh hashes remain recognizable. Tokens, nonces and verifiers must never enter diagnostics or nonsecret settings. The new secure envelope must be committed before clearing its pending nonce; legacy vault entries remain until successful migration. The native implementation is not yet complete at this checkpoint.

GET `/api/v1/companion/bootstrap` returns account identity, only the saved market preference, verified market choices, an available suggested market and provenance. A disabled/unavailable saved preference produces a fallback without rewriting the website preference or enabling collection. Source check time, actual upstream modification time and snapshot identity remain distinct. Device activity cannot supply installation or successful-sync timestamps: the authenticated server sync handler records completion only after its final page. It confirms server delivery, not an unverifiable local disk write.

Browser-only owned device list/rename/revoke endpoints are under `/api/v1/companion/devices`; administration uses separate `/companion/admin/devices`. Legacy device rename is additive at `/api/v1/devices/{id}` and retains its credential and expiry. Secret hashes and tokens never appear in device views. Password changes, account deactivation and revocation invalidate relevant native grants. Revocation does not erase local offline caches or historical observations.

Migration 0013 adds native authorization/device/used-refresh tables and one nullable credential foreign key. It does not rewrite existing accounts, credentials, preferences or market history. Downgrade refuses while native authorization records exist. An isolated PostgreSQL rehearsal verifies old field values, NULL legacy links, schema parity, refusal with populated grants, empty downgrade and re-upgrade. Actual retained legacy API image testing against schema 0013 returns 200 for its valid legacy token and 401 for a valid new `companion` token, so rollback fails closed rather than silently broadening native scopes. Production migration still requires a fresh validated backup and preservation audit over the original columns.

Standards: [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252), [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636), [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700). Existing application-specific origin, CSRF and session protections also apply. This document does not claim an installed native or browser end-to-end acceptance result.

Native source metadata also includes `watermark_observation_id`, `valuation_generation` and `valuation_synthetic`. `observation_id` identifies the current source head at that watermark, which may differ from the greatest imported ID. An observation metadata request is bound to its requested watermark; later historical imports cannot revise that receipt. `generation` remains the actual source snapshot identity. The valuation signature covers UTC daily winners, exact 14/60-day membership and all synthetic provenance, so a 304 response alone is never permission to skip rolling-price updates. Equivalent valuation signatures can safely return an empty completed sync page while advancing the normal cursor; the desktop still performs an authenticated check.
