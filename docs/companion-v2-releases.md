# Companion release delivery: read side and remaining publisher gate

The development API now exposes a controlled installer catalogue at `/api/v1/companion/releases/current` and immutable version download routes at `/api/v1/companion/releases/{version}/windows-x64`. They require no GitHub account or expiring artifact URL. There is no web publication/upload endpoint. The running production API has not been changed.

Until a release has passed all Windows acceptance, owner visual approval and signing, the current catalogue reports `ready: false`, with no version or download URL. The setup guide displays that state honestly. Private CI beta artifacts do not become a stable release.

The read-only release store is configured by `COMPANION_RELEASE_DIRECTORY`; `current.json` names a version directory containing a bounded manifest and installer. Only stable 2.x versions, a fixed versioned filename, at most 64 MiB, complete acceptance flags, an explicit visual-approval commit, a matching configured Authenticode publisher thumbprint and updater public-key identity, a valid signature encoding, and the exact file SHA-256/length are accepted. Unknown fields, missing configuration, previews, failed acceptance, changed bytes, oversized documents, path traversal and symlinks fail closed. Downloads stream bounded chunks; receipt files never reveal server filesystem paths. Existing version files are independent of the current pointer, allowing a later audited pointer rollback.

Trust boundary: the owner-controlled publisher is the only writer. The API checks the publisher's trusted receipt and installer digest; it does not perform Windows Authenticode verification itself. Windows CI/publisher must verify Authenticode, updater signatures, artifact provenance and all required installed tests before writing an immutable version. The native updater must independently verify its pinned signing key and signature. Synthetic release-service test receipts are explicitly not cryptographic/signing evidence.

**Remaining:** implement the publisher and release workflow, configured immutable storage/mounts/resource bounds, execute Windows SDK/native updater acceptance, and verify actual signed artifacts plus promotion/rollback rehearsal. Owner-managed signing credentials/certificate costs, new visual approval and final promotion gates remain unresolved. No stable release is currently published. No temporary CI artifact is presented as an ordinary-user download.

## Native updater candidate

The candidate uses pinned `tauri-plugin-updater` **2.14.1**, with legacy ZIP/system-proxy features disabled for the raw current-user NSIS installer. The native process fetches at most 16 KiB of metadata over trusted HTTPS from the fixed Market production origin, then passes it to the supported `restore_update` API. This preserves ordinary newer-version comparison and additionally requires the signature's authenticated version to match the manifest. No downgrade comparator override or insecure TLS/transport option is enabled.

`TWICHUI_UPDATER_PUBLIC_KEY` is a build-time, owner-managed public trust key. Missing/blank keys make updates visibly unavailable without a network request. Account/server settings cannot redirect update delivery. Download metadata must name the exact controlled version route; payloads are capped at 64 MiB and verified against exact size/SHA-256 before the SDK independently verifies the signature and signed version. Installation re-verifies, follows explicit Review / Close and update confirmation, and first quiesces the native worker/approval threads without deleting cache, cursor, settings or credentials. Download/verification failure leaves synchronization running; a launch/preparation failure has an explicit restart recovery path. Rust owns the updater; no generic updater/download privileges are granted to the WebView.

The release API's bounded dynamic metadata route returns no update when release trust/acceptance is missing, or when the current release is equal/newer. Its extra digest/size/provenance fields are validated by the native wrapper. Controlled version downloads remain independently addressable for rollback. An actual signed update install/upgrade is still required before stable publication; implementing this path is not proof of owner signing or production readiness.

Synthetic cryptographic acceptance uses a non-executable 1 KiB text payload, an ephemeral test key's **public key only**, and a real Tauri CLI signature bound to 2.0.0. Windows tests invoke the supported SDK to reject tampered bytes and inflated version metadata while preserving normal version comparison. The mock runtime supplies package metadata, not a fake cryptographic verifier. The private test key was never committed and has been discarded. These fixtures cannot authenticate a production release, and they are never configured as the application's trust key.
