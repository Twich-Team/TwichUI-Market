# Companion release delivery: read side and remaining publisher gate

The development API now exposes a controlled installer catalogue at `/api/v1/companion/releases/current` and immutable version download routes at `/api/v1/companion/releases/{version}/windows-x64`. They require no GitHub account or expiring artifact URL. There is no web publication/upload endpoint. The running production API has not been changed.

Until a release has passed all Windows acceptance, owner visual approval and signing, the current catalogue reports `ready: false`, with no version or download URL. The setup guide displays that state honestly. Private CI beta artifacts do not become a stable release.

The read-only release store is configured by `COMPANION_RELEASE_DIRECTORY`; `current.json` names a version directory containing a bounded manifest and installer. Only stable 2.x versions, a fixed versioned filename, at most 64 MiB, complete acceptance flags, an explicit visual-approval commit, a matching configured Authenticode publisher thumbprint and updater public-key identity, a valid signature encoding, and the exact file SHA-256/length are accepted. Unknown fields, missing configuration, previews, failed acceptance, changed bytes, oversized documents, path traversal and symlinks fail closed. Downloads stream bounded chunks; receipt files never reveal server filesystem paths. Existing version files are independent of the current pointer, allowing a later audited pointer rollback.

Trust boundary: the owner-controlled publisher is the only writer. The API checks the publisher's trusted receipt and installer digest; it does not perform Windows Authenticode verification itself. Windows CI/publisher must verify Authenticode, updater signatures, artifact provenance and all required installed tests before writing an immutable version. The native updater must independently verify its pinned signing key and signature. Synthetic release-service test receipts are explicitly not cryptographic/signing evidence.

**Remaining:** implement the publisher and release workflow, native pinned-key signed update checks, configured immutable storage/mounts/resource bounds, actual signed artifact verification and promotion/rollback rehearsal. Owner-managed signing credentials/certificate costs, new visual approval and final promotion gates remain unresolved. No stable release is currently published. No temporary CI artifact is presented as an ordinary-user download.
