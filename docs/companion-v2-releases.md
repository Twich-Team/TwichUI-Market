# Companion release delivery: read side and remaining publisher gate

**Current production delivery is the approved private signed-update beta:** [combined acceptance](combined-release-acceptance.md), [Get Desktop Companion](https://market.twich.gg/companion), [authenticated 2.0.0-beta.2 download](https://market.twich.gg/api/v1/companion/private-beta/2.0.0-beta.2/windows-x64). Owner-only admission, exact original bytes and free Tauri signatures are verified; commercial Windows publisher signing is not required. The stable channel is still unpublished. Earlier stable/read-side/signing-gate descriptions below are historical; use [current operations](combined-release-operations.md) for the deployed beta.

The development API now exposes a controlled installer catalogue at `/api/v1/companion/releases/current` and immutable version download routes at `/api/v1/companion/releases/{version}/windows-x64`. They require no GitHub account or expiring artifact URL. There is no web publication/upload endpoint. The running production API has not been changed.

Until a release has passed all Windows acceptance, owner visual approval and signing, the current catalogue reports `ready: false`, with no version or download URL. The setup guide displays that state honestly. Private CI beta artifacts do not become a stable release.

The read-only release store is configured by `COMPANION_RELEASE_DIRECTORY`; `current.json` names a version directory containing a bounded manifest and installer. Only stable 2.x versions, a fixed versioned filename, at most 64 MiB, complete acceptance flags, an explicit visual-approval commit, a matching configured Authenticode publisher thumbprint and updater public-key identity, a valid signature encoding, and the exact file SHA-256/length are accepted. Unknown fields, missing configuration, previews, failed acceptance, changed bytes, oversized documents, path traversal and symlinks fail closed. Downloads stream bounded chunks; receipt files never reveal server filesystem paths. Existing version files are independent of the current pointer, allowing a later audited pointer rollback.

Trust boundary: the owner-controlled publisher is the only writer. The API checks the publisher's trusted receipt and installer digest; it does not perform Windows Authenticode verification itself. Windows CI/publisher must verify Authenticode, updater signatures, artifact provenance and all required installed tests before writing an immutable version. The native updater must independently verify its pinned signing key and signature. Synthetic release-service test receipts are explicitly not cryptographic/signing evidence.

**Current:** the audited immutable publisher, inactive bounded rootless storage overlay, real offline-signature container rehearsal and owner-only two-phase release workflow are prepared. Windows SDK cryptographic acceptance passes on a real signed non-executable fixture; actual owner-signed installer/updater execution remains gated by signing inputs and manual tray acceptance. See [operator procedure](companion-v2-release-operations.md). Owner-managed signing credentials/certificate costs, new visual approval and final promotion gates remain unresolved. No stable release is currently published. No temporary CI artifact is presented as an ordinary-user download.

## Native updater candidate

The candidate uses pinned `tauri-plugin-updater` **2.14.1**, with legacy ZIP/system-proxy features disabled for the raw current-user NSIS installer. The native process fetches at most 16 KiB of metadata over trusted HTTPS from the fixed Market production origin, then passes it to the supported `restore_update` API. This preserves ordinary newer-version comparison and additionally requires the signature's authenticated version to match the manifest. No downgrade comparator override or insecure TLS/transport option is enabled.

`TWICHUI_UPDATER_PUBLIC_KEY` is a build-time, owner-managed public trust key. Missing/blank keys make updates visibly unavailable without a network request. Account/server settings cannot redirect update delivery. Download metadata must name the exact controlled version route; payloads are capped at 64 MiB and verified against exact size/SHA-256 before the SDK independently verifies the signature and signed version. Installation re-verifies, follows explicit Review / Close and update confirmation, and first quiesces the native worker/approval threads without deleting cache, cursor, settings or credentials. Download/verification failure leaves synchronization running; a launch/preparation failure has an explicit restart recovery path. Rust owns the updater; no generic updater/download privileges are granted to the WebView.

The release API's bounded dynamic metadata route returns no update when release trust/acceptance is missing, or when the current release is equal/newer. Its extra digest/size/provenance fields are validated by the native wrapper. Controlled version downloads remain independently addressable for rollback. An actual signed update install/upgrade is still required before stable publication; implementing this path is not proof of owner signing or production readiness.

Synthetic cryptographic acceptance uses a non-executable 1 KiB text payload, an ephemeral test key's **public key only**, and a real Tauri CLI signature bound to 2.0.0. Windows tests invoke the supported SDK to reject tampered bytes and inflated version metadata while preserving normal version comparison. The mock runtime supplies package metadata, not a fake cryptographic verifier. The private test key was never committed and has been discarded. These fixtures cannot authenticate a production release, and they are never configured as the application's trust key.

Primary references: [Tauri updater](https://v2.tauri.app/plugin/updater/), [SDK restore_update](https://docs.rs/tauri-plugin-updater/2.14.1/tauri_plugin_updater/struct.Updater.html#method.restore_update), [SDK verification/install](https://docs.rs/tauri-plugin-updater/2.14.1/tauri_plugin_updater/struct.Update.html). The repository-pinned CLI 2.12.4 supports `signer sign --app-version`; normal `tauri build` supplies the version automatically.

## Audited store operator candidate

`python -m market.release_publisher publish /incoming/{version} --actor <operator>` imports only a complete trusted workflow bundle. `rollback {version} --actor <operator>` changes its active pointer. There is no corresponding web endpoint. The importer independently verifies bounded exact bytes, owner publisher/public-key identity, the real updater signature and its authenticated version through the Rust verifier; Windows CI remains responsible for actual Authenticode trust evaluation and acceptance/visual provenance. An arbitrary caller's JSON is not independent Windows/CI evidence.

The dedicated store has an identity marker, exclusive writer lock, immutable version directories and a **256 MiB admission limit**. It never prunes previous installers. A durable immutable intent receipt precedes an atomic `current.json` replacement, followed by a separate completion receipt; interruption leaves either the previous pointer or an already-verified new pointer, with its durable intent. Retry is idempotent and never overwrites a published version. Failed signature, capacity, changed version bytes or an unrelated/symlink directory fails closed. Rollback re-verifies an existing asset, preserves every version/audit record and never requests a client downgrade. Audit capacity is bounded at 4,096 records and fails closed rather than deleting records.

`compose.companion-releases.yaml` is an **inactive opt-in overlay**. API listeners mount this store read-only. Only the ephemeral publisher mounts it writable, with no network, read-only root filesystem, 80 MiB temporary space, 256 MiB memory, one CPU, no capabilities, no-new-privileges and bounded logs. Its root UID is confined to the existing rootless Docker mapping; it has no host privileges, database volume or market/account credentials. The tool image builds just the pinned Rust 1.100.0 offline verifier and reuses an explicitly supplied verified backend dependency image. No production volume, service or configuration was changed while preparing it.

The no-network/read-only-root rehearsal verifies the actual signed text fixture and publishes it to a disposable temporary store, demonstrating immutable copy, idempotent retry and durable prepared/committed audit. It does **not** establish actual Windows signing, owner approval, a production release or permanent live distribution. The rootless tool image has been built and its actual no-network/read-only-root rehearsal passes. The owner-only Windows producer is prepared with exact-source CI, signed-installer SDK upgrade capability, actual Authenticode verification, immutable installed-evidence hashes and exact-installer manual acceptance. It has not run with owner signing credentials. Remaining gates are owner inputs, successful actual signed installer/updater execution, manual tray actions, new visual approval and final production preflight/promotion.
