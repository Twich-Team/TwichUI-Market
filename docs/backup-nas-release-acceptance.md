## Executive findings

Automatic cleanup was **not removing data**. The enabled 7/90/365-day policy was safely paused because a one-time isolated restore receipt had expired. Existing daily backup scheduling did not perform isolated restorations or renew that receipt. Historical documentation also incorrectly described the live backup schedule as disabled. The live schedule is enabled, every86,400 seconds, retaining two UTC daily scheduled points, with one minimum recovery point; protected/manual/release copies are excluded from automatic rotation.

The administration release adds individual/bulk/protected deletion, native SMB storage configuration and testing, folder selection, verified migration with preserved originals, storage health, and retention/recovery visibility. Local remains active. No production NAS was configured, no production archive was deleted or migrated, and no production database was overwritten. The owner can configure the real NAS entirely in the browser.

**Final measured cleanup/storage results: pending completion of bounded catch-up and normal scheduled-cycle acceptance.** Retention remains 7 days raw, 90 days intraday, 365 days daily, with the existing 60-day supporting history. The separately approved derived-pricing-cache stage uses the same 90-day rule while protecting current heads and daily support.

Failed verification retries after 30 minutes; temporary databases are dropped, and interrupted cleanup is recorded durably. The service is limited to 512 MiB/0.25 CPU with a 32 GiB rehearsal database ceiling and 32 GiB host reserve. The existing owner-approved local-only recovery exception remains; **off-VM protection is not established until the owner configures and verifies an external destination**. The next actual scheduled backup is November 25,04:30:38UTC. Its future live restore has not yet occurred; recurring restore/pin transfer was exercised against real SMB and isolated PostgreSQL fixtures.

The current recovery archive has a short operation lease during cleanup. ## Browser administration

Open **Administration → Storage & backups**. Backups supports Create, Download, Restore verification, Protect and Delete. Select one or several rows, review the files and confirm deletion. A single deletion requires its filename. Protected copies require an additional explicit acknowledgement; newest/last-known-good recovery loss and completed reservations have separate warnings/acknowledgements. Active restore/migration use and unexpired cleanup leases cannot be overridden. No intermediate unprotect action is used. Ordinary automatic rotation still preserves protected backups. Results report each deleted, missing or retained copy accurately.

In **Backup Storage**, select SMB / NAS, enter a friendly name, private NAS address, default port 445, username/password, optional domain and known share. Save, Test connection, Browse NAS folders, navigate breadcrumbs/create a folder, select the directory, then save/test that final selection. The test verifies authentication/share/read/write/folder creation/rename/delete and actual capacity where supported, with unique temporary artifacts. Passwords are masked and never returned; blank retains saved credentials. Use a dedicated NAS account limited to this directory.

The library does not enumerate shares: enter a known share manually, then browse folders. This is displayed explicitly. SMB2/3 only, mandatory signing, SMB3 encryption required by default; an explicit trusted-LAN option allows signed SMB2 compatibility. No host mount, Docker socket, privilege or Linux administrator credential is required. Public/loopback/link-local/metadata destinations are refused; private LAN addresses remain supported. DNS, ports, connection attempts, browsing and directory counts are bounded. Existing mounted filesystem compatibility refers to the approved persistent backup root; native NFS and arbitrary host-directory configuration are outside scope.

After a successful destination test, preview migration to inspect count, bytes and capacity. **Copy, verify and activate** runs in the background, checks complete SHA256 hashes and preserves creation/protection metadata and originals. Failed/interrupted copies leave the previous active destination intact; verified existing files can be reused safely. Only after successful cutover can a separate **Remove verified original copies** confirmation remove originals, rechecking destination hashes and active recovery references first. Keep the previous destination reachable while retained originals remain tracked.

An unavailable NAS is reported disconnected/stale, never empty. Existing metadata is retained; missing files and network failures differ. Backups use streaming temporary files, complete decode/checksum verification and finalization before success. There is no silent local fallback. Scheduled storage failures become terminal jobs and retry after 30 minutes; reconnection does not require restarting Market. Normal collection/API requests remain independent.

## Engineering verification and deployment

Selected client: [smbprotocol 1.17.0](https://pypi.org/project/smbprotocol/), [upstream/MIT license](https://github.com/jborean93/smbprotocol). Published July 7, 2026, inspected November24. It provides native Python SMB2/3, signing/encryption, bounded streaming and filesystem information in the existing unprivileged Python/Docker stack. Dependencies are pinned and audited. SRVSVC enumeration/DFS/public NAS addressing are unsupported; quota/capacity information stays unavailable when not exposed.

Credentials reuse Market's AES-GCM keyring format with backup-specific associated data. Encrypted envelopes/configuration/jobs/audit state persist in the manager volume; the original owner keyring is separately mounted read-only and never stored in SQLite, logs, API output, Git or images. Password rotation is supported. [Operations and disaster recovery](backup-nas-operations.md) documents preserving the state volume, database, manifests, private service token and separately protected keyring, including older keys. libpq supports an independently hosted PostgreSQL server; no Komodo/shared-database/host migration was performed.
