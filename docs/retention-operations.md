# Historical retention operations and recovery

Defaults are a proposal: raw listings7days, intraday statistics/observations90days, daily history365days, collection logs90days, security logs365days. Daily calculations retain another60days of source daily observations/statistics to preserve rolling reference values. Current snapshots and latest market heads always survive, including disabled markets. Six-month, one-year and multi-year durations are selectable within safe ordered bounds.

Administrator GET `/api/v1/admin/retention/preview` is read-only, including in the isolated preview. It reports each candidate stage, exact candidate row counts, next batch(max5,000rows), approximate logical table/index bytes, PostgreSQL database allocation and explicitly unknown filesystem recoverability. Logical deletion does not promise disk shrink. No VACUUM FULL is used. Ordinary PostgreSQL autovacuum can reuse dead space. Space estimates are proportional to allocated table/index bytes and estimated live tuples; they are approximate, especially after recent ingestion or pruning.

PATCH `/api/v1/admin/retention` saves a proposal, full before/after in retention_policy_changes, and a security audit event. Every edit invalidates application authorization. Changing a proposal never enables background historical deletion. Legacy operational housekeeping only honors longer proposed windows; shorter windows require approved confirmed batches.

Before live application: record explicit owner approval of the exact saved policy, create a current custom-format archive and SHA256 manifest, restore it into isolated market_restore, and verify exact counts/prices/provenance/contracts. Keep an encrypted off-host archive under owner control. The API's backup gate requires both dump and successful restoration timestamps within24hours; the preview reports readiness. Policy authorization is operator-only using `market.retention.authorize_policy(db,actor,owner_approval_notes)`; there is no HTTP authorization endpoint. Invoke only after actual owner approval and verified restore, never merely because tests passed. No live policy was authorized in this milestone.

An administrator checks the explicit permanent-removal confirmation and POSTs the signed preview token to `/apply`. Tokens bind actor, policy revision/hash, fixed time and exact next-stage primary keys; they expire after15minutes. Changed candidates/policy, missing approval/backup or a busy collector fail closed. One call executes one bounded transaction and returns a receipt; another preview and confirmation are required for the next batch. Stages remove obsolete daily references, unreferenced old observations, raw listings, unneeded statistics, then operational/security logs. Retained provenance remains untouched. Snapshot retained flags turn false before partial pruning; rehydration clears partial remnants before reconstructing exact rows.

Sync requests using missing observation IDs, pruned statistics or daily support older than the recorded historical floor return existing409/full-refresh semantics. The Rust desktop client already creates a new staged generation on409 and retains its completed offline cache. No export version or monetary field changed. Retained chart results keep exact14/60-day calculations; unsupported older dates are not invented.

Stop application between batches simply by making no further calls or saving a policy proposal (clears authorization). There is no automatic historic pruning job. A failed transaction rolls back its batch. Committed deletions require backup recovery; reverting application code does not recover history.

Recovery procedure: keep collector on its current configuration until owner authorizes a recovery cutover; preserve new observations separately. Verify the archive checksum, restore to a fresh isolated database with pg_restore --exit-on-error, check foreign keys, schema version, current and daily prices, provenance, users and cursors. Compare current production changes since the archive before proposing a project-only database/service cutover. Never reset production or overwrite its volume as a rehearsal. Keep original snapshot/receipt exports and the pre-pruning archive. Restore selection/cutover is a separate deliberate operator action. Migration0011 downgrade refuses a saved policy or batch receipt and must also preserve verified identity evidence; retain the additive migration when rolling back frontend code.

## Automatic maintenance (owner-authorized implementation, production deletion unapproved)

The automatic worker reuses `candidates` and `execute_selected`; it does not use an alternate compaction path. The earlier manual-only description above is historical. Saving a policy revokes both manual and automatic authorization and disables the schedule. Installation alone creates no authorization. Manual application retains signed batch confirmation; **both paths now also require protected local and off-VM recovery evidence**.

`market.retention_worker.authorize_automatic(db, actor, notes, limits=Limits(...), expected_execution_hash=...)` is an operator-only operation after explicit owner approval. It records the saved revision/hash, deletion scope including exact engine-source digest, and all work limits. It leaves enabled=false. Only a separately enabled exact authorized document executes. Any changed policy, engine scope, limits or inactive/non-admin authorizer fails closed. The administrator can pause between transactions; a policy change also revokes approval. The API has no authorization endpoint.

Defaults: one worker, five-minute maintenance interval, at most 12 batches and 20 seconds of work, at most 5,000 rows per transaction (25 compressed feed payloads), 2-second statement timeout, 3-second transaction timeout, 250-ms lock wait, and a 30-second collector margin. Existing collector/sync advisory lock is acquired per batch. Session-level leader lock spans the cycle, prevents overlap and releases after crashes. Receipts count only committed rows; interrupted runs retain prior committed receipts and mark interruption on restart. Queries and receipts resume from remaining eligible records, without a fragile cursor.

A rehashed custom-format managed archive must remain present, protected and required by recovery, with a matching successful isolated restore within 24 hours. `RETENTION_RECOVERY_EVIDENCE` points to an operator-managed read-only JSON receipt binding backup ID, filename, SHA-256, restored archive SHA-256, off_vm_verified=true, off_vm_verified_at and independently verified external failure_domain. Absent/stale/mismatched evidence blocks execution. This file is never manufactured by deployment, policy saves or the scheduler. The archive manifest endpoint rehashes bytes under the existing backup lock. Off-VM verification and copying require the owner's authorized destination; a mounted NAS alone proves neither a recovery copy nor permission to create one.

The worker pauses for absent backup evidence, collector/sync contention, a due collector, physical free space at/below reserve, WAL above its authorized threshold, or failed/timed-out transactions. Production policy remains revision 2 / 7 raw / 90 intraday / 365 daily + 60 support / 90 operational / 365 security, unauthorized. Production cap stabilization is independent and retained even if this service remains inactive.

Hourly independent measurements track allocation, physical free space, remaining eligible rows and cumulative committed removals. Two measurements are required before claiming throughput. Administrator status distinguishes allocation guards, physical reserve, collection failures, missing authorization, disabled/stopped/failed maintenance, backlog growth, dead tuples, WAL and recovery readiness. Dead-tuple heap estimates exclude index/TOAST/fragmentation and never promise host disk shrink. No VACUUM FULL, rewrite or database recreation is authorized.

An attempt that yields to a due collector or busy collector/sync lock **before committing any batch** retries after 60 seconds, rather than repeatedly colliding at the same five-minute phase. Once any rows commit, the full authorized interval is retained, so an early retry cannot double a deletion budget.

Authorization also binds the scheduler implementation digest and the configured filesystem reserve. A later scheduler code change or reserve change requires reauthorization. The local archive rehash has a separate 30-second internal HTTP deadline and holds no collector lock; the reviewed 20-second deletion budget starts after recovery validation, so large but valid archives cannot consume every maintenance window without allowing progress. UTC day-only preview dates are displayed without converting them into a different local calendar day.
