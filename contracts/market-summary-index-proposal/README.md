# Broad Item Advisor summary interface — experimental L2 proposal

This directory reserves a **separate** `twichui-market-summary-index` format/schema boundary. It is an offline feasibility proposal (`experimental=true`), not a production capability, API, addon or pricing engine. Nothing advertises/loads it. The approved detailed bridge schema 3 is unchanged. Future activation/negotiation and migration require L3 authorization and tests.

The [closed tuple schema](schema.json) and [pure sizing/lookup proof](../../scripts/advisor_index_feasibility.py) keep broad summary coverage independent from the selected detailed history. A received item can eventually have broad ask-derived evidence even when it is outside the detailed selection. Conversely, neither tier may contain a newly received identity: return unavailable/insufficient evidence, never zero, and permit a future exact-history request through the companion workflow. WoW does not make live Market HTTP requests.

Minimal useful fields are exact item/variant identity; explicit priced/supply-only/absent/unknown/unsupported state; recent reference, canonical Market Value and observed minimum where supported; supply; observation age; and a source-qualified confidence code. Shared metadata binds full market/issuer, source observation and completeness, watermark/as-of, algorithm/history basis, availability semantics and content identity. All copper is decimal text. Vendor sell values, completed sales, disenchant probabilities/returns and reliable local competition are not invented fields.

Source is `market_server_asking_summary`, confidence is capped at `limited`, and `can_satisfy_local_competition=false` is mandatory. Delivery completeness describes all retained exact-identity summaries; it does not make every source observation complete or guarantee a supported price. Missing rows are unavailable. Unknown/incomplete observations cannot prove absence. Exact variants sharing an item ID or display name never collapse into one price. A future item-aggregate view must carry a separate identity basis/range and cannot impersonate one exact variant.

Actual consumers at addon merge `5133a43477237bf7cd97a429a680a751a9533f7c`: `AdvisorData` discovers bag/tracked/recipe/local identities; `Advisor.Decide` preserves active crafting reservations, pending plans, auction eligibility, unsupported variants, vendor thresholds (1.5× and configured gain), uncertainty and verified disenchant comparisons. `Sell.Suggest` requires local quality, current competing tier, complete/uncut fresh listings and no mixed variants. `Sell.Observation` also requires distribution-backed local evidence. Imported asking summaries must enter a separate research-evidence role and must not satisfy either local competition predicate. Equipment/keep/metadata and local scan behavior remain unchanged.

WoW item links cannot automatically be assumed to yield the server's exact normalized upstream descriptor/hash. A future resolver must prove the base/variant mapping, use a unique supported exact match, or return unsupported/insufficient evidence. Generic item-ID aggregates remain distinct. Default detailed selection size 100 does not constrain that resolver's broad candidate universe.

The synthetic all-priced shape uses 45,125 rows, three distinct 11-digit copper strings per row, supply 12 and age 300 seconds. This deliberately avoids assuming production's unknown distribution. Full and item-ID-modulo-16 partition source/heap/compile measurements are in the L2 report. The experiment includes exact copper text and a bounded lookup index, but minimal structural validation excludes the full future cryptographic consumer. Offline Lua compilation, assignment and explicit global GC are measured separately; none proves real-client safety.

Recommend evaluating stable item-ID partitions (same item's variants route together), per-part byte limits/hashes, a shared versioned coverage manifest and on-demand addon loading in L3. A skewed partition must refuse or follow a reviewed deterministic subdivision scheme; never prune the broad universe to detailed tracked items. All partitions eventually retained still consume the complete index's heap plus overhead. Actual WoW load semantics, startup order, global GC, incremental validation and memory gates decide safe partition count/size in L4. Publisher atomicity/last-good behavior and player-confirmed reload requirements belong to later delivery work. No runtime partition addons are implemented here.
